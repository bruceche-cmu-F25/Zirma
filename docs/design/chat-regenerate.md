# 重新生成与编辑：一轮对话可以有几个版本

> 状态：v0.4（2026-11-28）**已批准**（Bruce：「Approve, commit, PR」），第 8 节七条全部定了。前三条（旧回复留着可切、只限最后一轮、做过事的一轮不给按钮）Bruce 已经同意（「可以，写设计文档」）；第 8 节第 4 条他不要（「4不要」：重新生成不带模型单子）；第 6 条按他的说法定了（「可以放在一个预输入框里」：补充过的一轮，重新生成先打开预先填好的编辑框）；第 5、7 条按建议（「Approve 5 and 7」）。「改了再发」改叫「编辑」，和按钮同名。v0.3、v0.2、v0.1 同日。
> 依据：本仓库的 `packages/core/src/runs.ts`（`core_runs`、`submitRun`、`conversationBefore`、`receiptsOf`）、`schema.ts`、`executor.ts`（`EngineRequest.history`）、`packages/engine-pi/src/worker.ts`（`open`：每段对话一个 Pi 会话文件，`SessionManager.continueRecent`；`history` 只在会话是新的时候才带上）、Pi 的 `AgentSession.navigateTree` 和 `SessionManager.branch / appendLabelChange`（`@earendil-works/pi-coding-agent` 里的实现）、`packages/ui/src/Conversation.tsx`（`Turn`、`MessageBubble`、回复下面那一行）。上一轮对比 ChatGPT 列出的六件缺的事里的第 3、4 件（第 1、2、5、6 件是 #67）。
> 标记：**【事实】** 读代码核实过；**【建议】** 本方案的提案（已批准）；**【已定】** Bruce 已经同意的。

## 0. 结论

1. **最后一轮可以「重新生成」，也可以「编辑」你说的话再发。** 两种做法都给这一轮多一个**版本**，不是另开一段对话，也不是覆盖。
2. **旧版本留着。** 回复下面出现 ‹ 1/2 ›，可以来回切；你切到哪个版本，接下来的对话就从哪个版本接着说。【已定】
3. **只限最后一轮。** 更早的那几轮不给按钮：改了它，后面的对话就都对不上了。【已定】
4. **做过事的一轮不给按钮。** 那一轮加过待办、改过日历、提过一个等你点头的提议，重新生成就会再做一遍，变成两个待办。想换个说法，接着问就行。【已定】
5. **引擎那边也真的退回去。** 每段对话在 Pi 里有一个存在磁盘上的会话文件。新版本让 Pi 从这一轮之前分出一个新分支，旧的那段留在文件里不动。模型看到的上下文和你在屏幕上看到的是同一条线。
6. **数据库加两列，要一次迁移。** PR 需要 `reviewed` 标签。

## 1. 现在到哪了

【事实】

- **一轮 = 一个 run。** 你说的话是 `core_runs.goal`，回复在 `outcome.reply`；附件在 `core_files.run_id`；中途补充的话（steer）和回答的问题是这个 run 下面的事件；它做过的事（加待办、改日历……）也记成这个 run 下面的事件（`receiptsOf`：不是 `run.` 开头的那些），提议在 `core_proposals.run_id`。
- **对话 = 按时间排的这些 run。** 没有「版本」这回事：一个 run 不能替换另一个。
- **模型看到的历史，有两份。**
  - 核心每次把前几轮的文字放在 `EngineRequest.history` 里（`conversationBefore`，最多 6 轮、每段 1000 字）。
  - 但 engine-pi 只在**会话是新的时候**才把它塞进提示（`worker.ts`：`fresh && job.history`）。平时用的是 Pi 自己的会话文件：`sessions/<对话 id>/` 里的 JSONL，`continueRecent` 接着往下写，工具调用、思考都在里面。
  - 所以只改我们的数据库不够：Pi 的会话文件里还有旧的那一轮，模型会接着它说。
- **Pi 的会话是一棵树。** 每条记录有 `parentId`；`navigateTree(某条用户消息)` 把「当前位置」移到那条消息之前（同一个文件），下一句话就从那里长出新分支，旧分支原样留着。Pi 自己终端里的「改一条以前的消息」就是这样做的。`appendLabelChange` 可以给一条记录贴一个名字（模型看不到）。
- **界面上**：你的消息有一个复制按钮；回复下面一行有复制和朗读（#67）。没有别的动作。

## 2. 从第一性原理出发

- **回复不满意时，最便宜的修正是「再来一次」或「我换个问法」。** 重新打一遍字、再问一遍，旧的那轮还挡在对话里，模型也会被它带偏。
- **「再来一次」不该让你丢东西。** 新版本未必更好。留着旧的、能切回去，你才敢点。这也是「你在掌控」那条：知道发生了什么，能撤回。
- **重来不能重复做事。** Zirma 和 ChatGPT 不一样：它的回复会加待办、改日历、起草邮件。把这样的一轮再跑一遍，就是再做一遍。所以只给「只是说了话」的那一轮重来。
- **屏幕上的和模型看到的要是同一条线。** 不然你切到了第 1 版，模型却还记得第 2 版，接下来的回答就对不上了。

## 3. 通用语言

| 词 | 意思 | 不是 |
|---|---|---|
| 版本 | 同一轮的另一次回答：重新生成的，或改了你的话再发的 | 不是另一段对话 |
| 这一组版本 | 同一轮的所有版本，第一个是原来那一轮 | — |
| 用着的版本 | 这一组里接在对话里的那一个，其余的「放在一边」 | 不是删掉 |
| 重新生成 | 你的话不变，再要一个回答 | 不是「继续」（中断的那一轮接着做，已有） |
| 编辑 | 这一轮答完以后，改你这一轮说的话，再要一个回答 | 不是中途补充（steer：Zirma 还在写时你又说的话） |

## 4. 方案

### 4.1 什么时候有按钮

【建议】只在**最后一轮**、而且下面几条都成立时出现：

- 这一轮已经结束：答完了、失败了、被你停了，或中断了（中断的照旧还有「继续」）。
- 这段对话里没有别的在跑、在排队、在等你。
- 这一轮**没做过事**：没有回执，没有提议（不管提议还在不在等你）。
- 它是一段日常对话（对话页和旁边的 Zirma 面板），不是开发会话，也不是自动化自己跑的一轮。

不满足的时候按钮不出，也不出一个灰的：没有要解释的东西。

### 4.2 界面

- **重新生成**：回复下面那一行（复制、朗读的旁边）加一个「重新生成」图标，用这段对话现在的模型。想换个模型再来，先在输入框下面那一行换，再点它。【已定】按钮上不带模型单子。这一轮中途补充过的话，点它打开的是预先填好的编辑框（4.6），不直接重来。
- **编辑**：鼠标停在你的消息上（手机上点一下），复制旁边多一个「编辑」。点了，那条消息变成一个输入框，原话在里面，下面「取消」「发送」。Esc 取消，⌘↩ 发送。附件照旧带着，这一轮不能在这里增删附件。
- **‹ 1/2 ›**：一组版本多于一个时，回复下面那一行最左边出现。切到哪一版，你的话和回复都换成那一版的。只有最后一轮能切；更早的那几轮只显示接着往下说的那一版，没有切换。
- 新版本在写的时候，和平常一样边写边出，停止按钮照旧能停。停下的那一版也是一个版本。

### 4.3 数据

【建议】`core_runs` 加两列（一次迁移）：

| 列 | 意思 |
|---|---|
| `version_of` | 这一组的第一个 run 的 id；原来那一轮自己是 `NULL` |
| `set_aside` | `1`：这一版放在一边（不是用着的那版）；每组正好一个是 `0` |

- **重新生成 / 编辑**：新建一个 run，`version_of` 指向这一组的第一个，原来用着的那版设成 `set_aside = 1`。附件复制一份关联到新 run（文件本身不复制）。全在一个事务里。
- **切版本**：同一组里换哪个是 `0`。
- **放在一边的版本，别处都当它不在**：`conversationBefore` 给模型的历史、对话列表上的最后一句话、未读、等你的数字、⌘K 都只看用着的那版。
- **它们还在**：对话详情把同一组的版本一起带上，界面才能切。
- 删除和归档照旧作用在整段对话上。

### 4.4 接口

【建议】

- `POST /api/runs/:id/again`，`{ requestId, goal? }` → `SubmitRunResponse`（202）。不带 `goal` 是重新生成，带了是编辑；都用这段对话现在的模型。请求 id 照旧保证点两次只算一次。
  - 拒绝时说清楚为什么：`not_last`（不是最后一轮）、`did_something`（做过事）、`busy`（对话里有东西在跑）、`session`（开发会话或自动化）。
- `POST /api/runs/:id/use` → 把这一版设成用着的那版。只在最后一组、对话里没东西在跑时可以。
- `Run` 多两个字段：`versionOf`、`setAside`。

### 4.5 引擎：让 Pi 也退回去

【建议】规则只有一条：**每一轮都告诉引擎「我接在哪一轮后面」**（`EngineRequest.after`：前一轮用着的那版的 run id；第一轮是 `null`）。engine-pi 在发这一轮之前，把 Pi 会话的当前位置放到那一轮的末尾，然后照常发。

- **贴名字**：worker 发一轮时，给这一轮的用户消息贴 `zirma:run:<run id>`；这一轮结束时，给它的最后一条记录贴 `zirma:end:<run id>`。名字存在 Pi 的会话文件里，重启也在。
- **接着说（平常）**：当前位置已经是 `after` 的末尾，什么都不用做。旧的会话没有名字：只要当前位置就是文件的末尾，照旧接着说，和今天一样。
- **重新生成 / 编辑**：`after` 是被重来那一轮之前的那一轮。worker 找到 `zirma:end:<after>`，`navigateTree` 到那里（`after` 是 `null` 就回到第一条消息之前），然后发新版本的话。旧的那一轮留在文件里另一条分支上。
- **切版本后接着说**：`after` 是你切到的那一版；worker 发现当前位置不在它的末尾，就 `navigateTree` 过去。
- **找不到名字**（这个功能之前的旧会话，或文件丢了）：为这段对话开一个新的 Pi 会话文件，用核心的历史（只含用着的版本）起头，也就是今天「会话是新的」那条路。上下文少了工具调用的细节，但对话的话一句不差。

这样 Pi 那边不需要知道「版本」，只需要知道「从哪接着」。

### 4.6 回执、提议和中途补充

- **做过事的不给重来**（4.1），所以版本之间不会有「一个版本加了待办，另一个没加」这种事。
- **中途补充的话**（steer）和**回答过的问题**属于那一版。【已定】这一轮补充过时，点「重新生成」不直接重来，而是打开编辑框，里面预先填好原话，后面接上补充的话（每段一行）。你看一眼、删改，再发；发出去的就是一个编辑过的版本。没补充过的一轮，点了直接重来。回答过的问题不填进去：那是 Zirma 问的，新的回答可能不再问。
- **失败、停掉的那一轮**也能重新生成：这就是「重试」。【已定】

## 5. 搭建顺序

每一刀都能单独合，合了不改变现在的样子，直到 R3 出按钮。

1. **R1 核心**：迁移（两列）、`again` 和 `use`、历史和列表只看用着的版本、对话详情带上整组、`EngineRequest.after`。测试：版本的建立和切换、做过事和不是最后一轮的拒绝、历史里没有放在一边的版本、请求 id 重放。
2. **R2 引擎**：worker 贴名字、按 `after` 移动位置、找不到名字时新开会话。测试：假 worker 里的规则；再用真实模型跑一次：重新生成后问「你上一句说了什么」，答的要是新版本。
3. **R3 界面**：重新生成、编辑、‹ 1/2 ›。浏览器测试：中英文、电脑和手机宽度、没有文字重叠、按钮只在该出的时候出。

## 6. 这一轮不做

- 不改更早的那几轮（会把后面的对话都切掉）。
- 不在开发会话里做（它改文件，「做过事」几乎总成立；以后单独想）。
- 不做整棵对话树的浏览，只有最后一轮的 ‹ 1/2 ›。
- 编辑时不增删附件。
- 不给做过事的一轮出「撤回再重来」：撤回各模块的改动是另一件事。

## 7. 风险

- **Pi 的名字记录会不会改变当前位置**：`appendLabelChange` 也是往文件里加一条记录。R2 先用真实的 Pi 会话核实：贴名字后接着说，模型看到的上下文不多不少。如果它会挡路，退一步：worker 自己记一个 run id → 记录 id 的小表（存在会话目录里）。
- **一组版本的花费**：每次重新生成都是一次完整的模型调用，和再问一遍一样。回复下面那行照旧写着花了多少。
- **旧会话**：这个功能之前的对话，最后一轮重新生成时会走「新开会话」那条路，模型少了那段对话里工具调用的细节。只影响那一次，之后就有名字了。
